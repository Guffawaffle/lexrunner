## A. Store Contracts (RunStore)

**Contract Location:** [`src/store/CONTRACT.md`](../src/store/CONTRACT.md)

### Key Points

- **Schema Version:** `RUN_STORE_SCHEMA_VERSION = "1.0.0"`
- **ID Format:** ULID (lexicographically sortable)
- **Timestamp Format:** ISO 8601 UTC
- **Lifecycle:** `pending → running → completed | failed | cancelled`

### Required Fields

| Field | Type |
|-------|------|
| `runId` | ULID |
| `planId` | string |
| `state` | RunState |
| `createdAt` | ISO 8601 |
| `updatedAt` | ISO 8601 |

### Change Protocol

Any changes require:
1. Schema migration plan
2. Version bump (SemVer)
3. Cross-repo notification (Lex)
4. Chief Architect approval

## B. Vertical Slice — LexRunner + Lex

The single happy path that MUST work before 1.0.0 ships:

### The 4-Step Flow

1. **User runs CLI command**
   ```bash
   lex-pr-runner run --plan plan.json
   ```
   - Parses plan.json
   - Creates a Run record with state `pending`

2. **Run persists via RunStore**
   - `SqliteRunStore.createRun()` called
   - Run transitions: `pending → running`
   - Each gate execution logged as StepOutcome

3. **Lex + FrameStore used for memory/policy**
   - Frames created/retrieved via Lex's `FrameStore`
   - Policy rules applied from Lex canon
   - Tool-grounded mode enforcement active

4. **Minimal transcript printed**
   ```
   Run 01ARZ3NDEK... completed
   Gates: 3/3 passed
   Duration: 45.2s
   Artifacts: artifacts/run-01ARZ3NDEK/
   ```

### Re-Run Behavior

When user runs again:
- Previous Run visible via `listRuns()`
- New Run gets fresh ULID
- Frame references consistent across runs

## C. Red Line Tests — LexRunner

These are the architectural canaries. If they fail, something foundational broke.

### 1. Store Contract Invariant Test

**Location:** `tests/store/contract.spec.ts`

Tests:
- [ ] `createRun()` persists and is retrievable
- [ ] `createRun()` fails on duplicate runId (no upsert)
- [ ] `getRun()` returns null for missing (no throw)
- [ ] `updateRun()` validates state transitions
- [ ] `listRuns()` respects filters and pagination
- [ ] `close()` is idempotent

### 2. Tool-Grounded Mode Enforcement Test

**Location:** `tests/runs/enforcement.spec.ts`

Tests:
- [ ] Mode enforcement rejects ungrounded tool calls
- [ ] Grounded tools are allowed
- [ ] Violations are logged to run artifacts
- [ ] Mode can be switched via proper API

## D. Quiet Risks to Monitor

These aren't blockers, but the Chief Architect should hold them in mind:

### 1. Interface Drift (RunStore ↔ FrameStore)

**Risk:** LexRunner and Lex evolve "almost together but not quite."

**Mitigation:**
- Cross-repo mapping documented in CONTRACT.md
- Shared concepts use same formats (ULID, ISO 8601)
- Changes require cross-repo notification

### 2. Schema Migration / Versioning

**Risk:** Post-1.0.0, "blow away DB" stops being acceptable.

**Mitigation:**
- Version field in schema
- Clear error on version mismatch
- Migration path documented (even if "reset" for now)

### 3. 12 Parallel Agents on Fresh Abstractions

**Risk:** Agent PRs want to tweak the new interfaces.

**Mitigation:**
- Treat stores as **read-only surfaces** for this wave
- Interface changes = soft red flag, require approval
- Contract docs are the source of truth

### 4. Tool-Grounded Mode Enforcement Coupling

**Risk:** Changes in enforcement logic affect all downstream behavior.

**Mitigation:**
- Enforcement tests are red-line canaries
- Policy changes in Lex need corresponding LexRunner tests
- Mode switching is explicit, never implicit
