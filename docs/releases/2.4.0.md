# LexRunner 2.4.0 progressive help release

Status: candidate; publication and a clean registry consumer check remain pending.

This minor release adds `--help-all` and makes root help a shorter entry point to
the existing journey. It does not rename operations or change their authority.

## What changes

- `lexrunner --help` presents seven existing work, integration and setup families,
  with a first-use integration path and pointers to authored-work preparation.
- `lexrunner --help-all` lists every command family and compatibility alias.
  Command-specific and nested help remain complete, and typo suggestions still
  discover commands omitted from the first view.
- The plan example uses `--output plan.json`; stdout JSON is a summary rather than
  the saved plan. Help distinguishes GitHub reads, local writes, previews, gate
  execution, worker handoff and explicit merge authority.

Both CLI executable names, package exports, plan schemas, the 34-tool MCP inventory
and the exact Lex 4.0.3 dependency remain unchanged. Node.js 24+ is still required.
The selected-work functionality introduced in [2.3.0](2.3.0.md) remains available.

## Evidence and limits

The implementation passed independent review after a discovered typo-suggestion
regression was corrected. Twenty focused tests, native build/lint and the current
implementation CI passed before source merge. Release gates and public consumer
verification are separate requirements for this candidate.

Assisted-handoff documentation and controlled Git/SQLite composition tests explain
existing preparation, attachment, receipt and verification bindings. They do not
launch a real worker or provide native Windows preparation support. Preview is not
executed verification; neither help nor a supplied receipt grants merge authority.

Exploration and explicit compact-resumption scripts in the repository remain
development tools outside the npm package. Smaller context text is not evidence
of lower total token usage or cost; no general efficacy claim follows.

## Publication

The intended immutable tag is `lexrunner-v2.4.0`, created only after the exact
owner-signed release target is reviewed, checked and contained in `main`.
The existing stable-tag workflow must validate and publish through npm OIDC.
A clean registry consumer check must then verify public integrity, ESM/CommonJS,
CLI help/version, read-only behavior and MCP inventory before delivery is complete.
No local non-dry-run publication is part of this procedure.
