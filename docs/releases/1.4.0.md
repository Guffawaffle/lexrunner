# LexRunner 1.4.0 native-host boundary release

- Status: **release candidate**
- Prepared: **2026-08-04**
- Tracking issue: **#909**

LexRunner 1.4.0 packages the native-host workspace boundary, Windows bootstrap repairs, and
dependency updates proven while dogfooding from a native Windows development workspace. It keeps
the existing production Linux containment guarantee, defines the fail-closed seam for a future
native Windows backend, and does not claim unsupported Windows runtime parity.

## User-visible changes

- A versioned `WorkspaceBoundary` contract now owns workspace observation, process execution, and
  Git operations through lease-bound capabilities instead of allowing path authority to escape.
- The production Linux backend enforces process and filesystem containment, revalidates live lease
  identity, canonicalizes set-like receipt fields, and keeps machine-local paths out of bounded
  diagnostics.
- Runtime resolution selects the proven Linux backend and fails closed where no production backend
  exists, including native Windows.
- Native Windows bootstrap now preserves repository line endings, keeps generated documentation
  stable, makes formatting checks checkout-neutral, scopes bootstrap audit to production
  dependencies, and exercises portable regressions without hiding them behind skipped tests.
- Plan validation subprocesses have bounded timeouts and retain actionable diagnostics under
  hosted-runner load.
- LexRunner now consumes the audited Lex 4 public surface, applies unified diffs through
  argument-safe `git apply`, and has no currently reported production or development npm
  vulnerabilities.

## Compatibility

- This is a minor release because it adds a versioned workspace-boundary contract and runtime
  resolver without removing a declared 1.3.0 package export or canonical command.
- Node.js 24 or newer remains required.
- The validated runtime dependency is `@smartergpt/lex@^4.0.0`.
- Assisted orchestration remains the supported production claim. Native Windows bootstrap and
  portable regression evidence do not imply a production native Windows workspace backend or
  unattended/headless worker-launch authority.
- The Windows-to-native-WSL projection workflow remains the supported bridge when a source checkout
  is exposed through DrvFS/9P and direct containment is unsafe.

## Release evidence

The 1.4.0 release commit must pass lint, typecheck, build, the full test suite, both dependency
audits, install-script policy, package validation, packed ESM/CommonJS/CLI/MCP smoke, and
`npm run release:publish:check -- --allow-untagged`. The exact candidate must also receive the
repository's independent review PASS before a history-preserving merge to `main`.

A signed `lexrunner-v1.4.0` annotated tag may be created only after the signed release commit is
contained in `origin/main`. The stable workflow must then re-run the release gates and publish
through the package-scoped npm trusted publisher. Registry metadata and a clean private-package
consumer smoke on native Windows complete issue #909.

## Publication boundary

This is a release-owner-signed, trusted-workflow npm publication boundary. Agents may prepare,
review, and merge the release candidate, but may not publish from a local shell. Only the
`stable-release` job in `.github/workflows/release.yml` receives GitHub OIDC authority after the
exact tag target and commit signatures, signer fingerprint, manifest version, and `main`
containment are verified.

The workflow has no long-lived npm token. Its authorized publication command is:

```bash
npm publish --access restricted --tag latest --json
```

If publication fails, repair and rerun the trusted workflow; do not fall back to a local publish or
retarget the existing version.
