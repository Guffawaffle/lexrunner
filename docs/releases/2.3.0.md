# LexRunner 2.3.0 selected-work release

- Status: **published; public registry consumer verified**
- Published and verified: **2026-09-09**
- Supersedes: **2.2.0**

This minor release exposes a new optional CLI/MCP operation for turning one explicitly
selected work item into preparation input. It also preserves authored technical context
and constraints when an idea becomes a project plan and issue descriptions.

`lexrunner attempt materialize --input selected-work.json --json` and the read-only
`materialize_attempt_input` MCP tool share one pure handler. Both return explicit
preparation fields, an expected packet hash and correspondence to the supplied source
bytes and criterion IDs. The [walkthrough](../selected-work-materialization.md) includes
a complete example. Materialization does not write lifecycle state or launch a worker.

Preparation accepts an optional `expectedPacketHash`. Bound handoffs retain that hash;
changed packet input fails before preparation acquires resources. A defensive mismatch
after preparation reports possible effects for inspection. Existing requests without
the field remain supported, and MCP preparation retains its mutation gate. Older strict
consumers must upgrade before accepting the new field; removing it loses this binding.

## Evidence and limits

Source PRs967 and968 passed independent review and required CI. PR969 adds built
CLI/MCP equivalence and a supported-host actual preparation/persistence/replay fixture.
PR969 merged after all configured CI checks passed at f880d8b, including the corrected
actual preparation/persistence/replay fixture. Release PR970 passed independent review
and required checks before merge and tagging.
A clean registry consumer check on native Windows installed the public 2.3.0 tarball and passed ESM/CJS,
both CLI aliases, bounded read-only status and MCP discovery (34 tools). Native Windows
preparation remains unverified here because the required native helper is absent.

Supplied outcome and work-plan references are not authenticated or accepted by the
converter. Dependency-bearing selections fail explicitly; this is not a scheduler.
Preparation is separate from worker launch, observed work, verification and outcome
fulfillment. There is no protected service installation or authority activation.
The Lex dependency remains deliberately pinned at 4.0.3.

The exploration-trail and compact-resumption pilots in later PRs971 and972 are
source-only follow-ups; they are not included in the 2.3.0 release.
