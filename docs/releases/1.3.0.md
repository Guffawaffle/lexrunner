# LexRunner 1.3.0 dogfood release

- Status: **release candidate**
- Prepared: **2026-07-30**
- Tracking issue: **#881**

LexRunner 1.3.0 packages the backward-compatible capabilities and fixes discovered while
dogfooding 1.2.1 in the native Windows STFC-Mod workspace. It does not publish or mutate that
workspace, and it does not claim that the final real Windows/DrvFS-to-native-WSL replay has passed.

## User-visible changes

- Plan validation returns the individual failures instead of only an aggregate count.
- Explicitly selected plan artifacts resolve consistently across MCP status, order, and gate
  operations.
- The independent merge review gate is mandatory by default, bound to an exact candidate/base
  pair, invalidated by any candidate change, and bypassable only through an explicit warned
  `review_bypassed` receipt.
- `attempt preflight` can report when brokered native-WSL projection is required before an Attempt
  allocates state.
- Versioned projection and path-mapping contracts bind an exact committed Windows source base to a
  broker-owned native-WSL repository and worktree root.
- Shared CLI and MCP projection lifecycle operations cover prepare/reuse, read-only status,
  bounded quarantine inspection, and ownership-safe cleanup.
- Launch, worker attachment, receipt, independent verification, acceptance, and fan-in revalidate
  the immutable engine-authored mapping rather than trusting caller-supplied paths.

The operator and recovery workflow is documented in
[`docs/workflows/native-wsl-projection.md`](../workflows/native-wsl-projection.md).

## Compatibility

- This is a minor release because it adds CLI, MCP, schema, and SDK capabilities without removing
  a declared 1.2.1 package export or canonical command.
- Node.js 24 or newer remains required.
- The validated runtime dependency remains `@smartergpt/lex@^3.0.1`; Lex, AXF, and LexSona do not
  require coordinated publication for this release.
- Assisted orchestration remains the supported production claim. This release narrows npm
  publication from a human shell to one release-owner-signed stable-tag OIDC workflow; it does not
  broaden merge, credential, or external-service authority.
- #855 remains the separate authored active-plan lifecycle dogfood issue.
- #863 remains open until the real Windows/DrvFS-to-native-WSL STFC replay succeeds against the
  then-current explicitly declared source commit.
- #882 tracks the semver-major Lex 4 and ESLint 10 migrations required to clear the current
  transitive npm audit findings; those breaking dependency changes are not folded into 1.3.0.

## Release evidence

The implementation stack ending at `79eaaaac8f0a6a8f3acbf2f302d7eeecdb8ae735` passed the full
suite (5,800 tests passed, 45 skipped), package validation, packed ESM/CommonJS/CLI/MCP smoke, and
the final `main` CLI Smoke and Release canary workflows. Its mandatory independent review caught a
quarantine durability gap; the corrected exact head passed the replayed review.

The 1.3.0 release commit must independently pass lint, typecheck, build, tests, package validation,
packed-consumer smoke, and `npm run release:publish:check -- --allow-untagged`. A signed
`lexrunner-v1.3.0` tag must then pass the stable release workflow and publish through the
package-scoped npm trusted publisher.

## Publication boundary

This is a release-owner-signed, trusted-workflow npm publication boundary. Agents may prepare,
review, and merge the release candidate, but may not publish from a local shell. Only the
`stable-release` job in `.github/workflows/release.yml` receives GitHub OIDC authority to execute
after the exact target commit is signed by the authorized release-owner key and contained in
`main`:

```bash
npm publish --access restricted --tag latest
```

The workflow has no long-lived npm token. A human maintainer configures the package's one trusted
publisher once; registry metadata and a clean native Windows 1.3.0 consumer must still be verified
before beginning the #863 replay.
