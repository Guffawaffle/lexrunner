# LexRunner 1.5.2 exact Lex 4.0.3 alignment release

- Status: **release candidate**
- Prepared: **2026-08-28**
- Supersedes: **1.5.1**

LexRunner 1.5.2 is a patch release that makes the runtime identity already selected by the
SmarterGPT Windows control plane reproducible for every LexRunner consumer. It changes no
LexRunner CLI, MCP, package-export, schema, persistence, or authority semantics.

## Dependency and dogfood alignment

- The direct dependency and package lock bind exact public `@smartergpt/lex@4.0.3` bytes instead of
  selecting any compatible Lex 4 release at consumer install time.
- The default ecosystem dogfood set is Lex 4.0.3, Lex-MCP 4.0.3, AXF 2.1.1, and LexSona 2.0.2.
- The dogfood harness launches npm and installed package bins through the active Node runtime so
  candidate staging and public-surface checks are shell-neutral on native Windows.
- The exact-pinned disposable consumer forbids lifecycle scripts during its credentialed install.
  A separately allowlisted step copies the already-built, identity-checked native SQLite binding
  from LexRunner's gated dependency tree before the public `tools/list` smoke. The accepted receipt
  rejects and hashes any lock resolution outside the named npm registry except the staged LexRunner
  candidate tarball.
- Explicit `--lex`, `--lex-mcp`, `--axf`, and `--lexsona` dogfood overrides remain available.
- LexRunner remains the restricted `@smartergpt/lexrunner` package. This release does not change
  the public distribution policy of Lex or Lex-MCP or the independent release boundaries of AXF
  and LexSona.

## Compatibility and evidence

`lexrunner`, `lex-pr`, and `lexrunner-mcp` remain the published binary names. Node.js 24 or newer
and exact `@smartergpt/lex@4.0.3` are required. The candidate must pass lint, typecheck, build,
default and Git-backed tests, package-boundary validation, packed ESM/CommonJS/CLI/MCP consumer
smoke, dependency audit, exact ecosystem dogfood, publication dry-run, and independent general and
hostile review against the exact signed candidate.

This remains a release-owner-signed, trusted-workflow npm publication boundary. Local shells and
agents may not perform non-dry-run publication. Only the signed-tag stable workflow may publish
through npm's package-scoped GitHub OIDC trusted publisher after every authority and package gate
passes.
