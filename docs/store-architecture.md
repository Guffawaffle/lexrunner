# Store Architecture

## Overview

LexRunner 1.0.0 introduces `RunStore` as the persistence contract for run lifecycle data.

## RunStore Interface

The `RunStore` interface provides structured access to:

- **Runs** — Top-level execution records
- **Steps** — Individual gate outcomes within runs
- **Receipts** — Scope/risk escalation records

### Key Types

| Type          | Description                                   |
| ------------- | --------------------------------------------- |
| `RunRecord`   | A single run with state, timestamps, metadata |
| `StepOutcome` | A gate execution result                       |
| `Receipt`     | A scope change requiring approval             |

### ID Ownership

IDs are **caller-generated**, not store-generated:

- `runId` — Generated by orchestration layer
- `stepId` — Generated by gate executor
- `receiptId` — Generated by escalation logic

The same `runId` appears in:

- Artifact filenames
- NDJSON audit logs
- MCP status responses

### Timestamp Format

All timestamps are **UTC ISO 8601 strings**: `YYYY-MM-DDTHH:mm:ss.sssZ`

## Implementations

| Implementation     | Status | Use Case            |
| ------------------ | ------ | ------------------- |
| `InMemoryRunStore` | 1.0.0  | CLI runs, ephemeral |
| `SqliteRunStore`   | Future | Local persistence   |
| `PostgresRunStore` | Future | Multi-tenant/hosted |

## NDJSON Coexistence

`RunStore` provides **structured access** for queries and dashboards.
NDJSON audit logs remain the **human-friendly trace**.

They complement each other:

- NDJSON: Append-only, human-readable, git-friendly
- RunStore: Queryable, structured, dashboard-ready

## Extension Points

Custom backends implement `RunStore` interface. No changes to core runner needed.
